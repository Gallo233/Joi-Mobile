# Cross-platform conformance corpus

These files are executable vectors. Every Joi client — iOS today, Android next —
must run them and produce the listed answers. They exist because "the platforms
share a contract" was, until now, only half true.

## What was actually shared, and what only looked shared

`Contracts/*.schema.json` is a real cross-platform artifact: any language with a
Draft 2020-12 validator gets identical answers from it, and `Tests/test_contracts.py`
proves the fixtures still validate.

But a JSON Schema describes a document's *shape*. It cannot express:

- that a duplicate key makes a manifest inadmissible rather than last-key-wins;
- which of two incompatible envelopes sharing the label `joi.character.v1` a
  document belongs to, or that matching both is a refusal;
- that a key whose name contains `memory`, `token` or `credential` is refused
  wherever it appears, at any depth;
- **which stable code** each refusal produces — the codes are the product
  surface, since they select the sentence the user reads;
- how a package's content identity is computed, byte for byte;
- how the event stream is framed.

All of that lived in Swift only. A second client re-deriving it from prose would
agree in the easy cases and diverge in exactly the cases that matter — a
malicious archive, a legacy import, a hostile chunk boundary. Worse, it would
diverge *silently*, because nothing would be comparing the two.

## The three layers

| Layer | Contract | Shared today | Covered here |
|---|---|---|---|
| 1. Document shape | `character-package-manifest-v1.schema.json`, `companion-event-v1.schema.json` | Yes — any Draft 2020-12 validator | No; run the schemas directly |
| 2. Admission semantics | strict scanner, envelope discrimination, forbidden content, stable codes, content identity, stream framing | **No — this corpus is what makes it shared** | Yes |
| 3a. Archive semantics | the restricted ZIP profile | **No — `zip-profile.json` is what makes it shared** | Yes |
| 3b. Tree semantics | per-asset digests, media magic bytes, renderer-graph closure, installation leases, journaled removal | No | Not yet — see below |

## Files

| File | Pins |
|---|---|
| `content-id.json` | The content-tree identity algorithm. Generated by `Tools/make_conformance_corpus.py` from the written rule, then verified against the shipping implementation. |
| `strict-json.json` | What the owned strict JSON scanner accepts and refuses. |
| `manifest-validation.json` | Document-level admission: envelope discrimination, key exactness, forbidden content, and the exact code each refusal produces. |
| `sse-framing.json` | `/v1/chat/streams` frame boundaries, including the ones that broke in practice. |
| `zip-profile.json` | Complete archives, byte for byte, and which of the three refusals each earns. Generated by `Tools/make_zip_corpus.py`. |

## Content identity, stated once

```
frame(data) := uint64_be(len(data)) || data

H = SHA256()
H << frame("joi.character.content-tree.v1")
for path in sorted(paths):                    # ordered by UTF-8 bytes
    H << frame(utf8(path))                    # package-relative, '/' separated
    H << uint64_be(byte_length_of_file)
    H << frame(utf8(lowercase_hex_sha256(file_bytes)))
contentID = "sha256:" || lowercase_hex(H)
```

Three details a port will get wrong if it works from intuition:

- The per-file digest enters as its **64 characters of hex text**, not as its 32
  raw bytes.
- Ordering is over the **whole relative path as UTF-8 bytes**, so `a/b` sorts
  before `ab` (`/` is 0x2F) and `model.vrm` before `motions/idle.vrma`. A sort by
  path components, by UTF-16 code units, or by a locale collation produces a
  different identity for the same bytes.
- Every field is length-framed, so no combination of paths and digests can be
  reinterpreted as a different tree.

## Running them

Python, checking the corpus is well-formed and the generator is not stale:

```bash
python3 -m unittest discover -s Tests -p 'test_conformance*.py' -t .
```

Swift, checking the shipping iOS implementation conforms:

```bash
swift test --package-path Packages/CharacterRuntime --filter Conformance
swift test --package-path Packages/ChatFeature --filter Conformance
```

Kotlin, checking the Android core conforms:

```bash
cd android && ./gradlew :character-runtime:test :companion-core:test
```

## Rules for changing a vector

1. A vector changes only with a decision recorded in `docs/DECISIONS.md`. These
   are wire and identity semantics; changing one silently re-identifies every
   installed package.
2. Adding a case is ordinary work and needs no decision.
3. If an implementation disagrees with a vector, the vector is right until a
   decision says otherwise. That is the whole point of writing it down first.
4. `content-id.json` is generated. Edit `Tools/make_conformance_corpus.py` and
   regenerate; `--check` fails if the file on disk is stale.

## Three refusals, kept distinct

`zip-profile.json` asserts *which* refusal fires, not merely that one did, because
they mean different things to the person holding the file:

- `unsupportedArchiveProfile` — the archive is well formed and this reader will
  not open it. Re-export it and it works.
- `unsafeArchive` — the archive is attempting something. Re-exporting will not
  help, and it should not.
- `malformedArchive` — the bytes do not describe an archive.

A port that collapses these into one code passes nothing here.

## Not covered yet, and honestly so

Per-asset digest verification, media magic-byte checks, the Live2D
`.model3.json` reference closure and the VRM motion-table renderer graph need a
*tree* rather than a document or an archive, and the corpus format has no tree
fixture yet. Installation leases, the activation CAS and journaled removal are a
different shape again: they are stateful protocols rather than input-to-output
functions, and vectors are the wrong tool for them.

Until those land, an Android port of the tree layer is a re-derivation, not a
port, and should be treated as carrying the risk that implies.
